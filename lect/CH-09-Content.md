### 페이지 07. 보도자료 표준 문체의 특징

공공 보도자료체의 핵심 특징

- 객관적 서술체: "~하였다", "~로 나타났다"와 같이 감정을 배제한 문어체 사용
- 능동적 화자 명시: "통계청은 ~라고 밝혔다"처럼 발표 주체를 분명히 함
- 절제된 수식어: "매우", "놀라운"과 같은 주관적 수식어를 배제하고 수치로 설명

> **[Note]** 문체를 통일하기 전에, 우리가 목표로 하는 보도자료 표준 문체가 어떤 특징을 갖는지 먼저 정리하겠습니다. 첫째, 객관적 서술체입니다. "~하였다", "~로 나타났다"처럼 감정을 배제한 문어체를 사용합니다. 둘째, 능동적 화자 명시입니다. "통계청은 ~라고 밝혔다"처럼 누가 발표했는지 발표 주체를 분명히 밝힙니다. 셋째, 절제된 수식어입니다. "매우", "놀라운" 같은 주관적 수식어는 배제하고 수치로 설명합니다. 보도자료는 개인의 감상이 아니라 사실을 전달하는 공식 문서이기 때문에, 이 세 가지 특징을 일관되게 유지해야 합니다.

### 페이지 09. Python 코드, 문체 변환 API 호출

문체 통일 함수

```python
def assemble_full_text(data: dict) -> str:
    """헤드라인의 리드문과 본문 전체 단락을 하나의 텍스트로 합친다."""
    return data["헤드라인"]["리드문"] + "\n\n" + "\n\n".join(p["내용"] for p in data["본문"])

def unify_style(draft_text: str) -> str:
    prompt = f"""아래 초안을 통계청 보도자료 표준 문체로 통일해 주세요.
모든 문장을 객관적 서술체로 통일하고, 주관적 수식어는 제거하되
사실과 수치는 절대 변경하지 마세요.

초안: {draft_text}"""

    message = client.messages.create(
        model=MODEL_NAME, max_tokens=1000,  # MODEL_NAME은 이전 차시에서 정의한 상수를 재사용
        messages=[{"role": "user", "content": prompt}]
    )
    return message.content[0].text

draft = assemble_full_text(data)
unified_text = unify_style(draft)
```

> **[Note]** 방금 설계한 프롬프트를 실제 코드로 옮기면 두 개의 함수가 필요합니다. 먼저 assemble_full_text 함수는 표준 데이터 안에 흩어져 있는 헤드라인의 리드문과 본문의 여러 단락을, 줄바꿈 두 번으로 구분해서 하나의 문자열로 합칩니다. 그다음 unify_style 함수가 이 합쳐진 텍스트를 프롬프트에 담아 API를 호출하고, 문체가 통일된 결과 텍스트를 돌려받습니다. 이전 차시까지 개별적으로 생성되었던 문단들이 이 두 함수를 거치면서 하나의 일관된 문체를 갖춘 완결된 글로 통합됩니다. assemble_full_text처럼 반복적으로 필요한 조립 작업을 별도 함수로 분리해두면, 마지막 차시의 전체 파이프라인에서도 이 함수를 그대로 재사용할 수 있어서 편리합니다.

### 페이지 11. 수치·단위 오류 유형 정리

자주 발생하는 4가지 오류 유형

- %(퍼센트)와 %p(퍼센트포인트) 혼동
- 천 단위 구분 콤마 누락 (201250 → 201,250)
- 단위 표기 불일치 (억원, 억 원 혼용)
- 원본 수치와 생성 문장 속 수치의 불일치 (환각으로 인한 오류)

> **[Note]** 문체를 통일했다면 이제 검수 단계로 넘어갑니다. 지금까지 여러 차시에 걸쳐 강조해온 오류 유형 네 가지를 마지막으로 종합 점검하겠습니다. %와 %p의 혼동, "201250"처럼 천 단위 구분 콤마가 빠진 경우, "억원"과 "억 원"처럼 단위 표기가 혼용된 경우, 그리고 원본 수치와 생성 문장 속 수치가 일치하지 않는 환각으로 인한 오류입니다. 특히 문체 변환 과정에서 AI가 문장을 다시 쓰면서 새로운 오류가 생기지 않았는지 다시 한번 확인하는 것이 이번 검수의 핵심입니다.

### 페이지 12. Python 코드, 정규표현식 기반 자동 검수

단위 표기 자동 검수 함수

```python
import re

def check_formatting_errors(text: str) -> list:
    """정규표현식 기반 1차 표기 오류 필터. 완벽하지 않으므로 최종 확인은 사람이 담당한다."""
    errors = []
    if "억원" in text:
        errors.append("단위 표기 오류: '억원'은 '억 원'으로 띄어써야 함")
    if re.search(r'(?<!\d)\d{5,}(?!\d)', text):
        errors.append("천 단위 구분 콤마 누락 의심: 콤마 없는 5자리 이상 숫자 발견")
    if re.search(r'비중.{0,10}(증가|감소|확대|축소)', text) and "%p" not in text:
        errors.append("비중(구성비) 변화 표현에는 %p 표기가 필요한지 확인 필요")
    return errors

errors = check_formatting_errors(unified_text)
```

> **[Note]** 방금 정리한 오류 유형들을 실제로 정규표현식으로 자동 검사하는 함수가 check_formatting_errors입니다. 세 가지를 검사합니다. 첫째, 텍스트 안에 "억원"이라는 붙여쓴 표기가 있는지 단순 문자열 검색으로 찾아냅니다. 둘째, 콤마 없이 다섯 자리 이상 이어지는 숫자가 있는지 정규식으로 찾아냅니다. 이건 "201250"처럼 천 단위 구분 콤마가 빠진 경우를 잡아내기 위한 것입니다. 셋째, "비중"이라는 단어 근처 10자 이내에 "증가", "감소", "확대", "축소" 같은 표현이 있는데 "%p"라는 표기가 문서 전체에 없다면, 퍼센트포인트 표기가 필요한지 확인해보라고 경고합니다. 여기서 꼭 기억해야 할 점은, 이 검사가 완벽하지 않다는 것입니다. 정규표현식 기반의 자동 검수는 어디까지나 1차 필터일 뿐이고, 최종 확인은 반드시 사람이 담당해야 합니다.

```python
            "유형": "감수 응답 파싱 실패",
            "위치": "-",
            "지적사항": "AI 감수 응답이 잘리거나 JSON 형식이 아니어서 자동으로 해석하지 못했습니다.",
        }]

review_result = review_press_release(unified_text, data)
```

> **[Note]** 작성 단계와 마찬가지로 감수 단계도 review_press_release라는 함수로 만들어서, 최종본과 원본 데이터를 입력하면 지적사항 목록을 자동으로 받아볼 수 있도록 구현했습니다. 이 함수에는 두 가지 중요한 설계 포인트가 있습니다. 첫째, 근거자료라는 딕셔너리에 계산지표뿐 아니라 통계해석결과, 품목별지표, 역대최대여부, 최근3개월증감률까지 관련된 모든 근거 자료를 함께 담아서 감수자에게 전달합니다. 이렇게 해야 감수자가 "역대 최대"나 "몇 개월 연속 증가" 같은 표현을 근거 없는 과장으로 오판하지 않습니다. 둘째, max_tokens를 1500으로 넉넉하게 잡고, 프롬프트에 "지적사항은 최대 5건까지, 항목당 한 문장"이라는 분량 제약을 넣었습니다. 그리고 마지막으로 try-except 구문으로 감싸서, 혹시라도 AI 응답이 중간에 잘리거나 JSON 형식이 아니어서 파싱에 실패하더라도 예외를 던져서 전체 파이프라인을 멈추게 하지 않고, 대신 "파싱 실패"라는 안내 항목 하나를 반환하도록 만들었습니다. AI 감수는 어디까지나 3단계 안전장치 중 하나일 뿐이므로, 이 단계 하나가 실패하더라도 이미 끝난 표기 검사와 수치 검증 결과는 그대로 보여줄 수 있어야 하기 때문입니다.

### 페이지 17. 감수 결과 예시

AI 감수자가 반환한 지적사항 예시

```json
[
  { "유형": "문체 불일치", "위치": "본문 2단락", "지적사항": "이전 단락과 달리 개조식 표현이 남아있음" },
  { "유형": "과장된 표현", "위치": "부제", "지적사항": "'지속 확대'는 2개월치 데이터만으로 단정하기 이름" }
]
```

> **[Note]** 실제로 review_press_release 함수를 호출하면 이런 형태의 결과를 받게 됩니다. 화면의 예시를 보시면, 본문 2단락에 개조식 표현이 남아있다는 문체 불일치 지적, 그리고 부제의 "지속 확대"라는 표현이 2개월치 데이터만으로는 과장이라는 지적이 담겨 있습니다. 이렇게 AI 감수자는 사람이 놓치기 쉬운 세부적인 표현상의 문제까지 짚어낼 수 있습니다. 다만 이 감수 결과 역시 AI의 판단이라는 것을 잊지 마세요. 지적사항이 실제로 타당한지는 최종적으로 사람이 확인해야 합니다.

### 페이지 18. 수정 반영 워크플로우

감수 결과를 반영하는 절차

1. AI 감수 결과의 지적사항 목록 확인
2. 타당한 지적사항만 선별 (사람의 최종 판단)
3. 해당 부분만 재작성 프롬프트로 재생성하거나 직접 수정
4. 수정된 최종본에 대해 수치 교차 검증 재실행

> **[Note]** AI 감수 결과를 받았다고 해서 지적된 내용을 무조건 다 반영하는 것은 아닙니다. 절차는 이렇습니다. 먼저 지적사항 목록을 전부 확인하고, 그중에서 담당자가 타당하다고 판단한 지적사항만 선별합니다. 그다음 해당 부분만 다시 프롬프트로 재생성하거나 직접 손으로 수정합니다. 그리고 반드시 마지막 단계로, 수정된 최종본에 대해 수치 교차 검증을 다시 한번 실행합니다. 왜냐하면 수정하는 과정에서 실수로 새로운 오류가 생길 수도 있기 때문입니다.

### 페이지 19. 최종 검수 통과 기준 체크리스트

배포 전 최종 점검표 (이전 차시 보안 점검표와 연계)

1. 문체가 보도자료 전체에서 일관되게 유지되는가
2. 모든 수치가 원본 데이터와 교차 검증을 통과하였는가
3. AI 감수자가 지적한 사항이 검토되고 필요한 부분은 수정되었는가
4. 이전 차시에서 배운 보안 점검표(비밀키 관리, 개인정보 마스킹 등)도 함께 충족되는가

> **[Note]** 지금까지 배운 모든 검증 절차를 종합한 최종 체크리스트입니다. 문체가 보도자료 전체에서 일관되게 유지되는지, 모든 수치가 원본 데이터와 교차 검증을 통과했는지, AI 감수자가 지적한 사항이 검토되고 필요한 부분은 수정되었는지, 그리고 이전 차시에서 배운 보안 점검표까지 함께 충족되는지 확인합니다. 이 체크리스트를 모두 통과해야 비로소 사람의 최종 승인 단계로 넘어갈 수 있습니다.

### 페이지 20. 표준 데이터에 검수결과 필드 추가

표준 JSON 확장, 검수결과 필드 추가

```json
{

    ]
  }
```

### 페이지 21. 정리하기

1. 여러 차시에 걸친 초안을 하나의 표준 문체로 통일
  - 객관적 서술체, 능동적 화자 명시, 절제된 수식어라는 보도자료 표준 문체의 세 가지 특징을 배우고, unify_style 함수로 사실과 수치는 그대로 둔 채 표현만 통일하는 방법을 익혔습니다.
  - assemble_full_text 함수로 헤드라인의 리드문과 여러 본문 단락을 하나의 텍스트로 조립하는 방법도 함께 배웠습니다.
2. 정규표현식과 수치 교차 검증으로 표기 오류 자동 검수
  - %와 %p 혼동, 천 단위 콤마 누락, 단위 표기 불일치 같은 흔한 오류를 check_formatting_errors 함수로 자동 점검하는 방법을 배웠습니다.
  - cross_check_all_numbers 함수로 완성된 보도자료 전체의 모든 숫자를 원본 데이터와 다시 한번 대조하는 방법도 익혔습니다.
3. AI 감수자 역할 부여와 최종 반영 절차
  - 작성자와는 다른 제3자 감수자 역할을 AI에게 부여해, 수치 오류·과장된 표현·문체 불일치·논리적 비약을 지적받는 review_press_release 함수를 구현했습니다.
  - 감수 결과를 사람이 선별해서 반영하고, 수정 후에는 반드시 수치 교차 검증을 다시 실행하는 최종 워크플로우까지 확인했습니다.
