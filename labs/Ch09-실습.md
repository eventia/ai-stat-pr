## 3단계. 수치 교차 검증하기 — 검증이 실제로 문제를 잡아내는 순간 (API 호출 없음)

> 개념 참고: 강의안 페이지 13 (`cross_check_all_numbers`)

```python
from modules.review import cross_check_all_numbers

number_check = cross_check_all_numbers(unified_text, data)
print(json.dumps(number_check, ensure_ascii=False))
```

**직접 재현할 실제 상황**: 8차시 본문 예시("...상위 세 품목이 전체의 **82.0%**를 차지하였다")를 그대로 이어받았다면, 아래와 같은 결과가 나옵니다.

```json
{"통과": false, "불일치수치": ["82.0"]}
```

**이게 왜 중요한가?** "82.0%"는 의류(32.3%) + 가전(25.8%) + 식품(23.9%)을 합산한 값입니다. 이 합산은 `modules/stats.py`가 계산한 것이 아니라 AI가 문장을 쓰면서 **스스로 덧셈을 한 결과**입니다. `cross_check_all_numbers`는 이 숫자가 `계산지표`나 `품목별지표` 어디에도 없다는 것을 정확히 찾아냈습니다. 이것이 바로 CLAUDE.md의 첫 번째 원칙("수치 계산은 반드시 `modules/stats.py`의 파이썬 함수가 처리하며, AI 모델에게 계산을 맡기지 않는다")이 실전에서 왜 필요한지 보여주는 실제 사례입니다.

**두 가지 해결 방법**을 비교해 봅니다.

1. **본문에서 파생 수치 표현을 빼도록 프롬프트를 수정**한다 — "상위 3개 품목의 합산 비중처럼 제공되지 않은 계산을 새로 하지 말 것"을 8차시 `expand_to_paragraph` 프롬프트에 추가.
2. **`modules/stats.py`가 상위 N개 누적 비중을 미리 계산해 `계산지표`에 넣어준다** — 그러면 AI는 계산이 아니라 이미 검증된 숫자를 인용하기만 하면 됩니다.

이 프로젝트의 설계 원칙상 2번이 정답입니다. 지금 실습에서는 실제로 고치지 않고, **검증 함수가 실제로 이런 문제를 잡아낸다는 사실 자체**를 확인하는 것이 목적입니다.

## 4단계. (실제 비용 발생) AI 감수 실행하기

> 개념 참고: 강의안 소주제 3 (페이지 15~16, 제3자 감수자 역할 부여)

```python
from modules.review import review_press_release

review_result = review_press_release(unified_text, data)
print(json.dumps(review_result, ensure_ascii=False, indent=2))
```

**예시 실행 결과** (실제로 한 번 실행해 확인한 값 — 지적사항의 개수와 내용은 매번 달라질 수 있습니다)

```json
[
  {
    "유형": "수치 오류",
    "위치": "본문 2단락",
    "지적사항": "82.0%는 개별 품목 비중의 단순 합산으로, 원본 데이터에 없는 파생 수치입니다."
  }
]
```

AI 감수자가 3단계에서 찾은 것과 같은 문제를 별도로 다시 짚어낼 수도 있습니다 — 두 가지 검증(수치 교차 검증 + AI 감수)이 서로 다른 방식으로 같은 문제를 잡아내는 것을 확인해 보세요. `review_press_release`는 응답이 잘려 JSON 파싱에 실패해도 예외를 던지지 않고 "감수 응답 파싱 실패" 안내 항목을 반환하도록 만들어져 있어, 이 단계 하나가 실패해도 전체 파이프라인이 멈추지 않습니다.

## 완성도 점검

1. 문체 통일 이후에도 문장이 자연스럽게 종결되는가
2. `check_formatting_errors`가 빈 목록을 반환하는가
3. `cross_check_all_numbers`가 "재검토 필요"로 표시한 숫자가 있다면, 그 숫자가 어디서 왔는지(원본 데이터인지 AI가 새로 계산한 것인지) 설명할 수 있는가
4. AI 감수 지적사항 중 타당한 항목을 실제로 반영했는가
