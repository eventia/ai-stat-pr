### 페이지 2. 보도자료 표준 문체의 특징

공공 보도자료체의 핵심 특징

- 객관적 서술체: "~하였다", "~로 나타났다"와 같이 감정을 배제한 문어체 사용
- 능동적 화자 명시: "통계청은 ~라고 밝혔다"처럼 발표 주체를 분명히 함
- 절제된 수식어: "매우", "놀라운"과 같은 주관적 수식어를 배제하고 수치로 설명

보도자료는 개인의 감상이 아닌 사실을 전달하는 공식 문서이므로, 감정적 표현을 배제한 객관적 서술체를 일관되게 유지해야 합니다. 이러한 표준 문체의 특징을 명확히 인지하는 것이 이번 차시의 출발점입니다.

### 페이지 3. 문체 변환 프롬프트 설계

문체 변환 프롬프트 예시

```
아래 초안을 통계청 보도자료 표준 문체로 통일해 주세요.
```

이미 작성된 초안 전체를 입력으로 주고, 문체를 통일하는 것만을 목적으로 하는 별도의 프롬프트를 설계합니다. 내용을 새로 만드는 것이 아니라 표현 방식만 다듬는 작업이므로, 사실 변경 금지 조건을 특히 강조합니다.

### 페이지 4. Python 코드, 문체 변환 API 호출

문체 통일 함수

```python
def assemble_full_text(data: dict) -> str:
    """헤드라인의 리드문과 본문 전체 단락을 하나의 텍스트로 합친다."""
    return data["헤드라인"]["리드문"] + "\n\n" + "\n\n".join(p["내용"] for p in data["본문"])

def unify_style(draft_text: str) -> str:
    prompt = f"""아래 초안을 통계청 보도자료 표준 문체로 통일해 주세요.
모든 문장을 객관적 서술체로 통일하고, 주관적 수식어는 제거하되
사실과 수치는 절대 변경하지 마세요.

초안: {draft_text}"""

    message = client.messages.create(
        model=MODEL_NAME, max_tokens=1000,  # MODEL_NAME은 4차시에서 정의한 상수를 재사용
        messages=[{"role": "user", "content": prompt}]
    )
    return message.content[0].text

draft = assemble_full_text(data)
unified_text = unify_style(draft)
```

리드문과 본문 전체를 하나의 문자열로 합친 뒤, 문체 통일 함수에 전달합니다. 8차시까지 개별적으로 생성되었던 문단들이 이 단계를 거치며 하나의 일관된 문체를 갖춘 글로 통합됩니다.

> **[수정] assemble_full_text 함수로 분리**: 기존에는 `draft = data["헤드라인"]["리드문"] + ...` 문장이 이 페이지와 실습 문서에 매번 그대로 반복 작성되어 있었습니다. 10차시 `main.py`가 참조하는 `assemble_full_text`라는 이름의 헬퍼 함수가 실제로 정의된 적이 없었으므로, 여기서 함수로 분리해 재사용합니다.

### 페이지 5. 수치·단위 오류 유형 정리

자주 발생하는 4가지 오류 유형

- %(퍼센트)와 %p(퍼센트포인트) 혼동
- 천 단위 구분 콤마 누락 (201250 → 201,250)
- 단위 표기 불일치 (억원, 억 원 혼용)
- 원본 수치와 생성 문장 속 수치의 불일치 (환각으로 인한 오류)

9차시의 검수 단계에서는 지금까지 여러 차례 강조해온 오류 유형들을 마지막으로 종합 점검합니다. 특히 문체 변환 과정에서 새로운 오류가 발생하지 않았는지 다시 한번 확인하는 것이 핵심입니다.

### 페이지 6. Python 코드, 정규표현식 기반 자동 검수

단위 표기 자동 검수 함수

```python
import re

def check_formatting_errors(text: str) -> list:
    """정규표현식 기반 1차 표기 오류 필터. 완벽하지 않으므로 최종 확인은 사람이 담당한다."""
    errors = []
    if "억원" in text:
        errors.append("단위 표기 오류: '억원'은 '억 원'으로 띄어써야 함")
    if re.search(r'(?<!\d)\d{5,}(?!\d)', text):
        errors.append("천 단위 구분 콤마 누락 의심: 콤마 없는 5자리 이상 숫자 발견")
    if re.search(r'비중.{0,10}(증가|감소|확대|축소)', text) and "%p" not in text:
        errors.append("비중(구성비) 변화 표현에는 %p 표기가 필요한지 확인 필요")
    return errors

errors = check_formatting_errors(unified_text)
```

정규표현식으로 단위 표기의 대표적인 실수 패턴을 자동으로 찾아냅니다. 이 검사는 완벽하지 않으므로 자동 검수를 1차 필터로 사용하고, 최종 확인은 사람이 담당합니다.

> **[수정] 무력화된 검사 로직 교정**: 기존 코드에는 세 가지 문제가 있었습니다. ① 콤마 누락 검사는 조건에 걸려도 `pass`만 실행하는 죽은 코드였습니다. ② `억원(?!\s)` 정규식은 "억원" 뒤에 공백이 오면(예: "201250억원 증가") 오히려 못 잡아내는, 의도와 반대로 동작하는 조건이었습니다 → 공백 조건 없이 단순 부분 문자열 검사로 교체했습니다. ③ %p 검사는 문장에 "포인트"라는 글자 그대로가 있어야만 동작해 사실상 거의 트리거되지 않았습니다 → "비중"이 증가/감소 표현과 함께 쓰였는데 "%p"가 없는 경우를 확인하는 실질적인 휴리스틱으로 교체했습니다.

리드문과 본문 전체를 대상으로, 문서 안에 등장하는 모든 숫자를 원본 계산지표(및 품목별지표)와 일대일로 대조합니다. 불일치하는 숫자가 발견되면 목록으로 반환하여, 어느 부분을 재검토해야 하는지 즉시 알 수 있습니다.

> **[수정] 4차시 검증 로직과 통합**: 기존 `cross_check_all_numbers`는 `verify_numbers`(4차시)와 별도로 구현되어 있었고, 콤마 처리 방식이 서로 달랐을 뿐 아니라 연도·순위 같은 저위험 숫자를 걸러내지 않아 정상적인 최종본도 "불일치"로 잘못 판정할 수 있었습니다. 4차시에서 수정한 `find_unverified_numbers`를 그대로 재사용하도록 통합해, 두 검증 함수가 항상 같은 기준으로 동작하게 했습니다.

### 페이지 8. 감수(Review) 프롬프트 설계, AI 감수자 역할 부여

감수 프롬프트 예시

```
당신은 통계 보도자료 전문 감수자입니다. 아래 원본 데이터와 완성된 보도자료를 대조하여
다음 관점에서 문제점을 지적해 주세요: ① 수치 오류 ② 과장된 표현 ③ 문체 불일치 ④ 논리적 비약
```

### 페이지 9. Python 코드, 감수 프롬프트 호출 및 결과 파싱

감수 실행 함수

```python
def review_press_release(final_text: str, data: dict) -> list:
    # 감수자가 "역대 최대"·"몇 개월 연속 증가" 같은 표현을 근거 없는 과장으로
    # 오판하지 않도록, 계산지표뿐 아니라 통계해석결과·품목별지표 등 관련 근거
    # 자료를 전부 함께 제공한다.
    근거자료 = {
        k: data[k]
        for k in ("계산지표", "통계해석결과", "품목별지표", "역대최대여부", "최근3개월증감률")
        if k in data
    }
    prompt = f"""당신은 통계 보도자료 전문 감수자입니다. 아래 원본 데이터와 완성된
보도자료를 대조하여 수치 오류, 과장된 표현, 문체 불일치, 논리적 비약을 지적해 주세요.
지적사항은 최대 5건까지, 항목당 한 문장으로 간결하게 작성하십시오.

원본 데이터: {json.dumps(근거자료, ensure_ascii=False)}
완성된 보도자료: {final_text}

JSON 배열 형식으로만 답하십시오. 예: [{{"유형": "...", "위치": "...", "지적사항": "..."}}]"""

    message = client.messages.create(
        model=MODEL_NAME, max_tokens=1500,  # MODEL_NAME, parse_json_response 모두 4차시에서 정의한 것을 재사용
        messages=[{"role": "user", "content": prompt}]
    )
    try:
        return parse_json_response(message.content[0].text)
    except (ValueError, json.JSONDecodeError):
        return [{
            "유형": "감수 응답 파싱 실패",
            "위치": "-",
            "지적사항": "AI 감수 응답이 잘리거나 JSON 형식이 아니어서 자동으로 해석하지 못했습니다.",
        }]

review_result = review_press_release(unified_text, data)
```

작성 단계와 마찬가지로 감수 단계도 함수로 만들어, 최종본과 원본 데이터를 입력하면 지적사항 목록을 자동으로 받아볼 수 있도록 구현합니다.

> **[수정, 7차 세션] 근거자료 누락 + 응답 절단 시 파이프라인 전체 크래시 수정 (실제 실행으로 발견)**: 기존 코드는 두 가지 문제가 실제 실행 중 드러났습니다. ① 원본 데이터를 `계산지표` 또는 `품목별지표` 중 하나만 골라 감수자에게 전달해, 품목별지표가 있어도 감수자가 보지 못하는 경우가 있었습니다 → 관련 근거자료를 전부 함께 전달하도록 수정했습니다. ② 실제로 새 시나리오(반려동물용품 실습)를 끝까지 돌려보니, 지적사항이 많아진 응답이 `max_tokens=800` 한도에 걸려 JSON 배열이 닫는 대괄호 없이 잘렸고, `parse_json_response`가 이를 찾지 못해 `ValueError`를 던지며 **파이프라인 전체가 멈췄습니다.** `max_tokens`를 1500으로 늘리고 프롬프트에 "최대 5건, 항목당 한 문장" 분량 제약을 추가했으며, 그래도 파싱에 실패하면 예외 대신 안내 항목 하나를 반환하도록 `try/except`를 추가했습니다 — AI 감수는 9차시 3단계 안전장치 중 하나일 뿐이므로, 이 단계가 실패해도 이미 끝난 표기·수치 검증 결과는 그대로 보여줄 수 있어야 합니다.

### 페이지 11. 수정 반영 워크플로우

감수 결과를 반영하는 절차

1. AI 감수 결과의 지적사항 목록 확인
2. 타당한 지적사항만 선별 (사람의 최종 판단)
3. 해당 부분만 재작성 프롬프트로 재생성하거나 직접 수정
4. 수정된 최종본에 대해 수치 교차 검증 재실행

감수에서 지적된 모든 내용을 무조건 반영하는 것이 아니라, 담당자가 타당성을 판단한 지적사항만 선별적으로 반영합니다. 수정 후에는 반드시 수치 검증을 다시 실행하여 새로운 오류가 발생하지 않았는지 확인합니다.

### 페이지 12. 최종 검수 통과 기준 체크리스트

배포 전 최종 점검표 (1차시 보안 점검표와 연계)

1. 문체가 보도자료 전체에서 일관되게 유지되는가
2. 모든 수치가 원본 데이터와 교차 검증을 통과하였는가
3. AI 감수자가 지적한 사항이 검토되고 필요한 부분은 수정되었는가
4. 1차시에서 배운 보안 점검표(비밀키 관리, 개인정보 마스킹 등)도 함께 충족되는가

지금까지 배운 모든 검증 절차를 종합한 최종 체크리스트입니다. 이 체크리스트를 통과해야 비로소 사람의 최종 승인 단계로 넘어갈 수 있습니다.

### 페이지 14. 9차시 정리와 10차시 예고

9차시 핵심 요약

- 여러 차시에 걸쳐 생성된 초안을 하나의 표준 문체로 통일하는 방법을 익힘
- 정규표현식과 수치 교차 검증으로 표기 오류와 환각을 자동 검수함
- AI에게 감수자 역할을 부여하여 사람이 놓치기 쉬운 문제를 추가로 발견함

이번 시간에는 초안을 배포 가능한 완성본으로 다듬는 마지막 검증 단계를 완성했습니다. 마지막 10차시에서는 지금까지 만든 수집, 정제, 분석, 작성, 검수 기능 전체를 하나의 자동화 시스템으로 통합하는 실습을 진행합니다.
