## 0. 총평

파이프라인은 **실제로 동작한다.** 실제 API + 실제 LLM으로 2회 end-to-end 실행에 성공했고, 단위 테스트 50개가 모두 통과하며, 수치 검증 로직은 이번 프로젝트에서 실제 버그(콤마 누락, 음수 증감률 오탐) 2건을 잡아낸 실적이 있다. "AI는 문장만, 계산은 프로그램이" 라는 설계 철학도 코드 전반에 일관되게 지켜지고 있다.

## 1. PT 자료 검토 (Ch02~Ch10)

### Ch02. 텍스트 정제 및 데이터 구조화

- **잘 된 점**: 정형/비정형/반정형 구분, 데이터 딕셔너리 설계는 개념 설명으로 충분히 명확하고, `clean_and_structure`([modules/clean.py](../modules/clean.py))가 실제로 정제(공백/주석 제거)·표준화(단위 통일)·구조화(필드 라벨링) 3단계를 코드로 정확히 구현하고 있다. 개인정보 마스킹([modules/clean.py:18](../modules/clean.py))도 1차시 보안 원칙과 실제로 연결되어 있다.
- **문제 1 (실습과의 불일치)**: 이 PT 문서의 페이지19에는 "실제 API 키로 검증"한 결과 XML 응답·이중 URL 인코딩·요청 파라미터 형식 차이 등 3가지 실전 이슈가 `[수정]`으로 상세히 추가되어 있다. 그런데 [Ch02-실습.md](../labs/Ch02-실습.md)는 여전히 가상의 JSON 응답(`totalAmount`, `momRate` 등)만으로 실습을 구성하고 있어, 학습자가 실습만 따라가면 이 API의 실제 특성(XML, 인코딩 문제)을 전혀 모르고 넘어가게 된다. PT에서 발견한 실전 교훈이 실습에는 반영되지 않은 채 남아 있다.
- **문제 2 (일반화 과장의 씨앗)**: `clean_and_structure`가 반환하는 표준 데이터의 `계산지표`는 `raw.get("계산지표", {})`로 그대로 통과시킬 뿐이며, 어떤 필드가 와야 하는지에 대한 검증이 없다. 이후 차시(5, 7차시)에서 "총거래액", "전월대비증감률" 같은 특정 필드명을 하드코딩해서 참조하기 시작하는데, 그 결합이 시작되는 지점이 바로 여기다.

### Ch03. 주요 NLP 기법

- **잘 된 점**: 형태소 분석(`kiwipiepy`) → TF-IDF 키워드 → TextRank(PageRank) 주요문장 추출까지 실제로 동작하는 코드([modules/nlp.py](../modules/nlp.py))이며, "단일 문서에서 TF-IDF의 한계"를 스스로 인정하고 문장 단위 코퍼스로 보완한 점, `summa` 대신 `networkx`로 직접 구현하도록 바꾼 점 등은 실제 실행 검증을 거친 성실한 보강이다.
- **문제 (구조적 단절, 중요)**: 이 차시 전체(키워드 추출, 주요 문장 추출, 문서 주제 요약)의 결과물인 `NLP분석결과`(핵심키워드, 주요문장)는 **실제 파이프라인에서 최종 산출물에 전혀 반영되지 않는다.** [main.py:39](../main.py)에서 `analyze_document`를 호출하긴 하지만, 그 결과는 이후 어떤 함수의 입력으로도 다시 사용되지 않는다 — `generate_headline_set`([modules/write.py:94](../modules/write.py))은 `계산지표`와 `통계해석결과.특이점목록`만 사용하고, `NLP분석결과`를 참조하는 유일한 함수인 `build_summary_prompt`/`generate_summary`([modules/write.py:36-60](../modules/write.py))는 **`main.py`에 아예 import되어 있지 않다.** 즉 3차시 전체와 4차시의 절반(요약 생성 부분)이 "만들어졌지만 쓰이지 않는" 상태다. Ch03-실습.md 자신도 페이지4에서 "최종 보도자료 작성은 이 NLP 추출 결과가 아니라 5차시의 검증된 계산 결과를 근거로 진행됩니다"라고 인정하고 있어, 이 결과물이 장식적 성격이라는 것은 문서도 알고 있다. 그렇다면 이 두 차시를 마치 파이프라인의 필수 단계처럼 배치("표준 데이터에 통합", "다음 차시에서 재사용됨")한 서술은 과장이며, "참고용 보조 분석(선택 실습)"이라고 명확히 표시하는 편이 정직하다.

### Ch04. LLM 기반 텍스트 요약

- **잘 된 점**: 프롬프트 설계 4원칙, `MODEL_NAME` 상수화(이후 모든 차시가 재사용), `parse_json_response`의 방어적 파싱(코드펜스 대응, 이후 실제로 배열/객체 파싱 버그를 고친 이력 있음 — [modules/write.py:12-31](../modules/write.py)), `find_unverified_numbers`/`verify_numbers`의 콤마·저위험 숫자 처리 등은 실전에서 검증된 견고한 설계다.
- **문제 1 (Ch03과 동일한 단절)**: `generate_summary`(3줄요약+제목후보)는 [바로 위 Ch03 항목]에서 설명한 대로 `main.py`에서 호출되지 않는 죽은 코드다. 테스트는 있지만(간접적으로 `parse_json_response` 등 공용 함수 경유) 파이프라인 통합 테스트([tests/test_ch10_pipeline.py](../tests/test_ch10_pipeline.py))에는 `generate_summary` 호출이 없다.
- **문제 2 (재현성 안내 부족)**: 페이지7·9차시 실습의 "실행 결과"들은 실제 LLM(temperature > 0 가능성)이 생성한 문장을 마치 결정론적 정답처럼 제시한다. LLM 호출은 실행할 때마다 문장이 달라질 수 있는데, 이 사실이 Ch04 어디에도 명시되어 있지 않다. 학습자가 자기 실행 결과가 문서와 다르면(예: 문장 표현이 조금 다르면) "내가 뭔가 잘못했나" 오해할 소지가 있다. temperature 관련 언급은 페이지8에 있지만 "재현성" 관점의 안내는 없다.

### Ch05. 통계적 패턴 기반 텍스트와 통계자료 해석

- **잘 된 점**: 증감률/비중/순위 계산(`pandas`), 임계값 기반 특이점 탐지(`detect_special_points`), 템플릿 기반 해석문 생성이라는 "계산은 프로그램, 해석문은 규칙 기반 1차 생성" 구조는 이 프로젝트 전체에서 가장 견고하게 구현된 부분이다. `add_calculated_indicators`가 5차시의 핵심 산출물이라는 점, 이후 모든 차시가 이를 재사용한다는 설계도 실제 코드와 일치한다.
- **문제 1 (자동화 주장과 실제 구현의 괴리, 가장 중요한 발견)**: 페이지6("역대 최고, 최저 판별 로직")은 `history_df`(과거 시계열)와 비교해 `is_record_high = history_df["거래액"].iloc[-1] == history_df["거래액"].max()`처럼 **실제로 계산하는 코드**를 보여준다. 그러나 실제 통합 함수 `add_calculated_indicators`([modules/stats.py:46](../modules/stats.py))는

  ```python
  is_record_high = data.get("역대최대여부", False)
  ```

  로, **이미 계산되어 입력에 들어있다고 가정**한다. 페이지6에서 보여준 "과거 이력과 비교하는" 코드를 실제로 호출하는 함수는 프로젝트 전체에 존재하지 않는다. `최근3개월증감률`도 마찬가지로 어딘가에서 계산되는 것이 아니라 `data.get("최근3개월증감률")`로 그냥 입력값을 읽기만 한다([modules/clean.py:36-38](../modules/clean.py)도 raw에 있으면 통과시킬 뿐). 즉 "역대 최대 경신"이라는, 보도자료에서 가장 임팩트 있는 특이점 판단의 **원재료를 사람이 과거 데이터를 직접 조사해서 입력해줘야 한다** — 코드 주석 자체도 이를 인정한다("이 함수 자체가 과거 이력을 조회하지는 않는다", [modules/stats.py:44-45](../modules/stats.py)). 이는 Ch10이 표방하는 "원자료 입력 하나로 완전 자동 실행"이라는 목표와 정면으로 배치된다. PT 문서가 이 갭을 명확히 알리지 않고 페이지6 코드가 실제로 파이프라인에 연결된 것처럼 서술한 것은 수정이 필요하다.
- **문제 2 (실제로 재현된 결함)**: `detect_special_points`는 "전월/전년동월 대비 큰 폭 **감소**"와 "최근 3개월 연속 **증가/감소**세"까지 감지할 수 있는데([modules/stats.py:4-19](../modules/stats.py)), `add_calculated_indicators`의 해석문장 생성 블록([modules/stats.py:55-69](../modules/stats.py))은 "역대 최대치 경신", "전월 대비 큰 폭 증가", "전년동월 대비 큰 폭 증가" **세 가지만** 처리한다. `generate_interpretation`의 템플릿 딕셔너리에도 "큰 폭 감소"·"연속 감소세" 항목이 없다([modules/stats.py:22-30](../modules/stats.py)). 결과적으로 **통계가 하락하거나 감소세가 지속되면 `특이점목록`에는 표시되지만 `해석문장`은 생성되지 않고 조용히 비어 있게 된다.** 이는 가정이 아니라 실제로 이번 프로젝트의 6차 세션에서 가격정보 API로 실행했을 때 그대로 재현된 문제이며(하락 케이스 처리를 위해 `price_stats.py`에 별도 `_해석문` 함수를 새로 만들어야 했음), 원본 `modules/stats.py`는 아직 고쳐지지 않았다. 온라인쇼핑 예시가 우연히 항상 증가하는 값만 다뤄서 지금까지 드러나지 않았을 뿐, 5차시 PT의 핵심 함수에 남아있는 실제 결함이다.
- **문제 3 (고아 함수)**: `check_percent_unit`(페이지12)은 단위 테스트만 있고([tests/test_ch05_stats.py:36-39](../tests/test_ch05_stats.py)) `add_calculated_indicators`나 다른 어떤 파이프라인 코드에서도 호출되지 않는다. "%와 %p 자동 구분 검증"이 파이프라인에 실제로 배선되어 있는 것처럼 페이지13("통합 파이프라인")까지 이어지지만, 실제로는 검증 로직 자체가 어디에도 실행되지 않는다.

### Ch06. 표, 그래프 기반 설명문 자동 생성

- **잘 된 점**: 막대/원형 그래프 생성과 설명문 생성이 실제로 잘 연결되어 있다(`build_visual_descriptions`, [modules/charts.py:42-60](../modules/charts.py)). `matplotlib.use("Agg")` 강제 지정은 이 프로젝트 환경에서 실제로 겪은 Tcl/Tk 문제에 대한 정확한 대응이다.
- **문제 1 (고아 기능)**: 페이지2·5·8에서 3대 그래프 유형(막대·꺾은선·원형) 중 하나로 꺾은선그래프(추세)를 소개하고, `generate_chart_description`에 `line` 분기까지 만들어 두었지만([modules/charts.py:26-31](../modules/charts.py)), 이 분기는 **실제 파이프라인에서 호출될 방법이 없다.** `build_visual_descriptions`는 막대·원형만 생성하고([modules/charts.py:55-59](../modules/charts.py)), `load_input`([modules/io.py:9-41](../modules/io.py))은 엑셀의 **첫 번째 행만** 읽으므로애초에 "여러 달치 시계열" 데이터를 구성할 방법이 파이프라인 어디에도 없다. `line` 분기는 단위 테스트에서만 호출되고([tests/test_ch06_charts.py:30-35](../tests/test_ch06_charts.py)) end-to-end로는 도달 불가능한 코드다. 커리큘럼상 "3대 그래프 유형을 알아야 한다"는 교육 목적은 이해되지만, 실습 문서(Ch06-실습.md)는 이 사실을 언급하지 않고 마치 완결된 기능인 것처럼 다룬다.
- **문제 2 (고아 함수)**: `generate_table_description`(페이지10)도 마찬가지로 정의만 되어 있고 `main.py`/`build_visual_descriptions` 어디에서도 호출되지 않는다.
- **문제 3 (사소, 이식성)**: `plt.rc("font", family="Malgun Gothic")`(페이지3, [modules/charts.py:46](../modules/charts.py))은 Windows 전용 폰트다. 이 프로젝트는 Windows 환경이라 문제없지만, PT 어디에도 "이 코드는 Windows 전용이며 다른 OS에서는 한글이 깨진다"는 안내가 없어, 다른 환경의 학습자가 그대로 따라 하면 한글이 네모(tofu)로 깨지는 그래프를 만들게 된다.

### Ch07. 통계 보도자료 작성 실습1 (핵심지표 요약)

- **잘 된 점**: `load_input`으로 xlsx/PDF를 분기 처리하는 구조, 6하원칙 기반 헤드라인 생성 프롬프트, `select_core_indicators`로 필수 지표만 골라내는 로직이 모두 실제 코드와 일치하며 잘 동작한다. `build_headline_prompt`에 콤마 포맷을 미리 넣어야 하는 이유를 코드 주석으로 정확히 남긴 점([modules/write.py:73-76](../modules/write.py))은 이번 세션에서 실제로 겪은 버그의 교훈이 잘 반영된 사례다.
- **문제 1 (재사용성 과장, B-1의 핵심 근거)**: `REQUIRED_FIELDS = ["총거래액", "전월대비증감률", "전년동월대비증감률"]`([modules/write.py:9](../modules/write.py))과 `지표_단위 = {"총거래액": "억 원", ...}`([modules/write.py:69](../modules/write.py))는 "온라인쇼핑 거래액" 지표명에 하드코딩되어 있다. `load_input`의 xlsx 분기도 `row["총거래액"]`, `row["전월대비증감률"]` 같은 **고정된 컬럼명**을 직접 참조한다([modules/io.py:17-23](../modules/io.py)). Ch10 페이지9는 "표준 데이터 구조를 유지하면 다른 통계표에도 동일한 파이프라인을 재사용할 수 있다"고 하지만, 실제로는 이 3개 파일(`write.py`, `io.py`, `stats.py`)을 전부 새 지표명에 맞춰 다시 작성해야 한다. 실제로 이번 프로젝트에서 가격정보 API를 붙일 때 `modules/price_stats.py`, `modules/price_report.py`를 **통째로 새로 작성**해야 했던 것이 이 한계의 직접적인 증거다(반대로 `modules/review.py` 전체와 `expand_to_paragraph`/`generate_body_paragraphs`는 지표명에 의존하지 않아 그대로 재사용되었다). "동일한 파이프라인 재사용"이 아니라 "검증·문체통일 절반은 재사용 가능, 계산·헤드라인 절반은 매번 재작성 필요"가 정확한 설명이며, PT가 이 구분을 명시했어야 한다.
- **문제 2 (사소)**: `load_input`의 xlsx 분기가 만드는 `제목`은 항상 `f"{연월} 온라인쇼핑 동향"`으로 고정되어 있어([modules/io.py:17](../modules/io.py)), 페이지2에서 "제목"을 원자료에서 유연하게 가져오는 것처럼 보이지만 실제로는 다른 통계에 재사용할 때 이 줄도 함께 고쳐야 한다.

### Ch08. 통계 보도자료 작성 실습2 (그래프 설명)

- **잘 된 점**: 그래프 설명문을 두괄식 본문 단락으로 확장하는 `expand_to_paragraph`/`generate_body_paragraphs`는 6차시의 `시각자료설명`(소주제 필드 포함)에만 의존하고 지표명에는 의존하지 않아, 실제로 이 프로젝트에서 검증 없이 그대로 재사용된 몇 안 되는 함수 중 하나다. 연결어 처리도 단순하지만 실용적이다.
- **문제 (죽은 코드 자체 인지, 이미 수정됨)**: 페이지7의 `[수정]` 주석이 스스로 밝히듯, 기존에는 `prev_summary` 변수를 만들어놓고 쓰지 않는 죽은 코드가 있었다. 이번 검토 시점에는 이미 제거되어 있어 문제 없음 — 다만 이런 유형의 "설명과 코드 불일치"가 다른 차시(Ch05의 역대최대 판별 등)에도 아직 남아 있다는 점에서, Ch08의 이 사례처럼 실제 실행 후 발견·수정하는 절차가 다른 챕터에도 더 필요하다.
- **문제 (본문-그래프 매핑의 암묵적 가정)**: `generate_body_paragraphs`는 `시각자료설명` 리스트의 각 항목을 그대로 한 단락으로 확장하는데, `build_visual_descriptions`가 반환하는 두 항목(막대그래프용, 원형그래프용)은 **동일한 이미지 파일 경로**를 가리킨다([modules/charts.py:51-59](../modules/charts.py), 두 dict 모두 `이미지경로: 이미지경로`). 즉 본문에는 "품목별 동향"과 "품목별 비중" 두 단락이 생기지만 실제 이미지는 한 장(막대+원형이 나란히 있는 subplot)뿐이다. 최종 문서에 그래프를 삽입하는 단계(10차시)가 추가되면 이 매핑이 헷갈릴 수 있는데, 어느 문서에도 "두 단락이 이미지 한 장을 공유한다"는 설명이 없다.

### Ch09. 통계 보도자료 작성 실습3 (문체, 자동교정, 감수 모델)

- **잘 된 점**: 이 차시가 프로젝트 전체에서 **가장 완성도가 높다.** `unify_style`, `check_formatting_errors`, `cross_check_all_numbers`, `review_press_release` 모두 실제로 파이프라인에 연결되어 있고, 이번 세션에서 실제 버그(콤마 누락, 음수 증감률 오탐)를 잡아낸 것이 바로 이 차시의 검증 함수들이다. `find_unverified_numbers`를 4차시와 공유하도록 통합한 것도 좋은 설계다. `review_press_release`가 `품목별지표`·`통계해석결과`까지 근거자료로 함께 전달하도록 보강된 점([modules/review.py:104-108](../modules/review.py))도 실전에서 검증된 개선이다.
- **문제 1 (%p 검사의 오탐 가능성)**: `check_formatting_errors`의 %p 검사([modules/review.py:92](../modules/review.py))는 "비중"이라는 단어 10자 이내에 "증가/감소/확대/축소"가 있는데 "%p"가 없으면 무조건 경고한다. 그러나 "비중은 32.4%로 나타나 확대되었다"처럼 %p가 필요 없는(포인트 차이가 아니라 값 자체를 말하는) 정상 문장도 걸릴 수 있는 휴리스틱이다. 다만 이 결과는 담당자가 참고하는 경고 목록일 뿐 파이프라인을 막지 않으므로 치명도는 낮다 — 다만 페이지12 최종 체크리스트에서 이 한계를 명시했어야 한다.
- **문제 2 (검증의 사각지대)**: `_is_low_risk_number`가 1~2자리 숫자를 전부 검증 대상에서 제외하는 것은 "순위·개월수" 오탐을 막기 위한 실용적 타협이지만, 반대로 실제 오류(예: 9위인데 8위로 잘못 인용)를 놓치는 사각지대이기도 하다. 이 트레이드오프가 페이지11("검증을 통과하지 못하면 재검토")에 언급되지 않는다.

### Ch10. AI 기반 보도자료 자동 생성 시스템 구축

- **잘 된 점**: `main()` 설계가 실제 `main.py`와 거의 그대로 일치하고([main.py:30-59](../main.py)), 이전 버전에서 빠져 있던 자동 검수 단계·그래프 단계를 다시 통합한 `[수정]` 이력도 실제 코드와 부합한다. 로그 인코딩(`encoding="utf-8"`) 수정도 실제로 겪은 문제에 대한 정확한 대응이다.
- **문제 1 (표에 언급된 함수 중 실제로 배선 안 된 것들)**: 페이지3의 "핵심 함수 목록" 표는 `add_calculated_indicators`, `build_visual_descriptions`, `generate_headline_set`, `generate_body_paragraphs` 등 실제로 `main()`이 호출하는 함수만 나열하고 있어 이 표 자체는 정확하다. 그런데 이 표에는 **4차시의 `generate_summary`가 아예 빠져 있다** — 이는 은연중에 "4차시 요약 기능은 최종 파이프라인의 일부가 아니다"라는 것을 인정하는 셈이면서도, Ch04 PT/실습 어디에도 "이 기능은 main.py에 통합되지 않는 참고용 실습"이라고 명시적으로 밝히지 않은 것과 대비된다. 표를 만든 사람은 이 단절을 알고 있었던 것으로 보이나, 그 인지가 Ch04 문서로 역전파되지 않았다.
- **문제 2 (자동화 수준에 대한 과장, A-1/A-2 요약)**: 페이지9 "시스템 확장 방향"은 "다른 통계표 적용", "배치 처리", "웹 인터페이스 연동"을 향후 확장으로 제시하는데, 그보다 먼저 **현재 시스템 안에서도 자동화되지 않은 부분**(역대최대/추세 판별을 사람이 입력, 감소 케이스 해석문 누락)이 있다는 점이 이 페이지에 전혀 언급되지 않는다. "완전 자동화 시스템을 완성했다"(페이지11)는 결론은 헤드라인·본문 생성·검수 구간에는 맞는 말이지만, 특이점 판별 구간에는 정확하지 않다.
- **문제 3 (사소)**: 페이지7 `save_final_document`는 파일명을 `data['문서정보']['제목']`으로 그대로 사용하는데, 이 값에 `/`나 `:` 같은 파일명에 쓸 수 없는 문자가 들어갈 가능성(예: 제목에 날짜 표기가 다르게 들어오는 경우)에 대한 방어가 없다. 온라인쇼핑 예시에서는 항상 안전한 제목만 나오므로 지금까지 드러나지 않았을 뿐이다.

## 2. 실습 자료 검토 (Ch02~Ch10)

PT 자료 검토에서 이미 다룬 구조적 문제(3~4차시 단절, 역대최대 미자동화, 감소 케이스 누락, 재사용성 과장)는 실습 자료에도 동일하게 나타나므로 반복하지 않고, **실습 문서 특유의 문제**만 정리한다.

- **Ch02-실습**: 위에서 언급한 대로, PT에서 발견된 실제 API의 특성(XML 응답, 이중 인코딩)이 실습에는 전혀 반영되지 않아 가상의 JSON 예시로만 진행된다. 학습자가 이 실습만으로 실제 공공 API 연동을 시도하면 반드시 막힐 것이다.
- **Ch03-실습**: 실행 결과를 실제로 재검증하고 `[수정]`으로 정직하게 갱신한 점(예: 키워드 순위가 예상과 다르게 나온 이유까지 설명)은 이 프로젝트의 실습 문서 중 가장 모범적인 사례다. 다만 이 실습의 최종 산출물(`NLP분석결과`)이 이후 어느 차시에서도 다시 등장하지 않는다는 점은 PT와 동일한 단절 문제를 그대로 노출한다.
- **Ch04-실습**: 페이지3의 LLM 생성 결과("삼줄요약", "제목후보")가 마치 항상 이렇게 나오는 것처럼 고정된 값으로 제시된다. 실제로는 매 실행마다 문장이 달라질 수 있는데(`temperature` 기본값이 명시되지 않음, API 기본값 사용) 이 점에 대한 주의가 없다. 게다가 이 실습의 결과물(`요약결과`)도 Ch10 `main()`에는 전혀 반영되지 않는다.
- **Ch05-실습**: 품목별 표 데이터를 사용한 예시는 실제 코드(`detect_special_points`, `generate_interpretation`)와 정확히 일치하며 재현 가능하다. 다만 이 실습도 "감소" 케이스는 다루지 않아(모든 예시 품목이 증가만 함), PT에서 지적한 A-2 결함이 실습에서도 드러나지 않은 채 넘어간다. 실습 예시에 감소하는 품목(예: 생활용품 -2.1%)이 이미 등장하는데도 이 경우 `해석문장`이 만들어지지 않는다는 사실은 실습 어디에도 언급되지 않는다 — 오히려 좋은 반례가 될 수 있었던 데이터가 그냥 지나쳐진 셈이다.
- **Ch06-실습**: 막대+원형 그래프만 다루며 꺾은선(추세)은 실습에 아예 등장하지 않는다 — PT에서 지적한 "고아 기능"이 실습에서는 언급조차 되지 않아, 학습자는 애초에 이 기능이 있는지도 모르고 넘어갈 가능성이 크다.
- **Ch07-실습**: 실제 코드와 가장 잘 맞아떨어지는 실습 중 하나. 글자 수 검증(제목 16자, 부제 15자)이 "15자 내외/25자 내외" 조건을 사람이 눈으로 확인하는 수준에 머무는 점은 아쉽지만(자동 판정 함수가 없음), PT에서도 자동화하겠다고 약속한 적은 없으므로 문제라기보다는 개선 여지다.
- **Ch08-실습**: `expand_to_paragraph`가 지표명에 의존하지 않는 범용 함수라는 점이 실습에서도 그대로 확인되며, 실제로 이번 프로젝트의 가격정보 파이프라인에도 수정 없이 재사용되었다. 이 챕터는 PT·실습·실제 구현이 가장 일관성 있게 맞아떨어지는 사례다.
- **Ch09-실습**: 페이지5의 `data["본문"][2]["내용"].replace("이어가며", "이어가고 있는 것으로 나타났다")`는 AI 감수 지적사항을 "코드로 반영"하는 것처럼 보이지만, 실제로는 그 문자열이 정확히 그렇게 나온다는 보장이 없는 **우연한 예시**다(LLM 출력이 매번 다를 수 있음, Ch04 항목 참고). 개념 예시로는 무방하나, "이것이 실무에서 반복 가능한 코드"라는 인상을 주지 않도록 "예시일 뿐, 실제로는 지적사항 내용에 맞춰 매번 다르게 수정한다"는 주석이 있으면 더 정확했을 것이다.
- **Ch10-실습**: 페이지2의 `main()` 코드가 실제 [main.py](../main.py)와 완전히 동일하여 신뢰도가 높다. 페이지3~4의 실행 결과도 실제 재현 가능한 형태로 제시되어 있다. 다만 이 실습 역시 A-1(역대최대 자동판별 안 됨), A-3(NLP 결과 미사용) 문제를 그대로 물려받는다 — 특히 이 실습이 "과정 전체의 최종 결과물"이라고 자평하는 만큼, 여기서라도 "다음은 향후 개선 과제"로 이 두 가지 갭을 명시했다면 학습자에게 훨씬 정직한 마무리가 되었을 것이다.

## 3. 종합 결론

**"통계 수치 계산 → AI 문장 생성 → 수치 교차검증"이라는 핵심 파이프라인은 실제로 완성되어 있고 신뢰할 수 있다.** 특히 9차시의 검증 체계(콤마·부호·환각 검증)는 이번 프로젝트 실행 중 실제 버그를 잡아낸 것으로 실증되었으며, 8차시의 본문 확장 함수는 지표명과 무관하게 재사용 가능한 좋은 설계다.

그러나 "완전 자동화 시스템"이라는 표현은 다음 두 가지 지점에서 사실과 다르다.

1. **특이점 판단의 입력값 중 가장 임팩트가 큰 것("역대 최대/최저", "최근 3개월 추세")이 실제로는 자동 계산되지 않고 사람이 사전에 조사해서 입력해야 한다.** (A-1)
2. **하락·감소 방향의 통계에서는 특이점이 감지되어도 해석문장이 생성되지 않아, 자동화가 조용히 정보를 누락시킨다.** 이는 가상의 우려가 아니라 이번 프로젝트에서 실제로 재현된 결함이다. (A-2)

그리고 다음 두 가지는 "불필요하거나 과장된 부분"에 해당한다.

3. **3~4차시(NLP 키워드/주요문장 추출, LLM 3줄요약)의 산출물이 최종 보도자료 생성에 전혀 사용되지 않는다.** 별도 실습으로서의 교육적 가치는 있지만, 지금처럼 파이프라인의 필수 단계인 것처럼 배치하면 학습자가 전체 구조를 오해하게 된다. (A-3)
4. **"동일한 파이프라인으로 다른 통계표도 재사용 가능"이라는 주장은 절반만 사실이다.** 검증·문체통일·본문확장 로직은 실제로 재사용되지만, 계산·헤드라인 로직은 지표명이 하드코딩되어 있어 매번 새로 작성해야 한다. (B-1)

### 권장 조치 (우선순위순)

1. **(시급)** `add_calculated_indicators`/`generate_interpretation`에 "큰 폭 감소", "연속 감소세" 템플릿을 추가한다. 이미 가격정보 파이프라인(`price_stats.py`)에서 검증된 해법을 원본 `stats.py`에도 역이식하는 것이 가장 저비용 고효과 수정이다.
2. **(중요)** Ch05 PT/실습에 "`역대최대여부`/`최근3개월증감률`은 현재 자동 계산되지 않으며, 별도의 과거 이력 데이터 소스와 비교하는 함수를 구현해야 완전 자동화가 된다"는 사실을 명시하거나, 실제로 그 비교 함수를 구현해 `add_calculated_indicators` 앞단에 연결한다.
3. **(중요)** Ch03·Ch04의 NLP/요약 결과물을 "참고용 선택 실습"으로 명확히 재분류하거나, 실제로 `generate_summary`의 출력을 헤드라인 생성 프롬프트의 보조 자료로 연결한다.
4. **(개선)** `REQUIRED_FIELDS`, `지표_단위`, `load_input`의 컬럼명을 설정값(config)으로 분리해, "다른 통계표 재사용" 시 코드 수정 없이 설정만 바꾸면 되도록 리팩터링한다.
5. **(경미)** 꺾은선그래프(`line`)와 `generate_table_description`을 실제로 파이프라인에 연결하거나, "이 기능은 심화 학습용이며 현재 파이프라인에는 연결되어 있지 않다"고 명시한다.
6. **(경미)** LLM 호출 결과의 비결정성(문서의 "실행 결과"는 예시일 뿐 매번 달라질 수 있음)을 Ch04 PT에 한 줄 추가한다.
